# Kotlin/JVM Architecture

The compiler is layered so every build-time and runtime operation stays on the JVM.

```text
compiler-cli  ->  compiler-api  ->  compiler-core
                         |              |
                         +--------> compiler-backends
                         +--------> compiler-runtime
compiler-tests exercises every layer and the captured parity corpus
```

`compiler-core` owns source decoding, preprocessing, tokens, C types, declarations, semantic checks, constant evaluation, diagnostics, and typed IR. `compiler-backends` lowers IR to Kotlin-owned instruction/object representations for x86, ARM, ARM64, RISC-V, C67, ELF, PE/COFF, and Mach-O. `compiler-runtime` contains arithmetic, bounds, sanitizer, profiling, and runtime-link manifests. `compiler-api` provides embedding, execution, JVM-library, and typed build-configuration APIs. `compiler-cli` is the Gradle application and response-file-aware command-line layer.

Native target output is data generated by Kotlin code. The JVM artifact never invokes `System.load`, JNI, a C compiler, Make, or a native TinyCC library. `KotlinJvmLibrary` can load JVM JAR providers; native shared-library registration is rejected. Generated executables may be run through the pure Kotlin process boundary when a target backend has produced one.

The former C implementation and its captured outputs were temporary differential-test inputs only. The C source/build tree has now been removed; the retained `baseline/` files are inert compatibility evidence and are not build inputs.
